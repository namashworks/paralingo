System design CONTEXT · CONTAINERS

The speech profile layer sits beside an existing voice stack. The voice platform keeps doing telephony, turn detection, speech recognition and speech synthesis. Your orchestrator hands each finished user turn to the speech profile package, which analyses it, updates the speaker's file, and hands back guidance. LLM agents and other tools read and write the same file through tools or MCP.

Solid arrows are calls or data handed over. The return path along the top of the voice platform is the spoken reply.

Who calls what

  • The orchestrator owns the audio, so it opens and closes sessions and submits every user turn (analyze_utterance).
  • The LLM agent gets read and observe tools only: summary, guidance, sections, trends, observations, accent.
  • Other agents (QA review, coaching, analytics) connect over MCP and see the same file.
  • External models such as speech emotion recognition or accent ID pass their results in through the external field.

Design boundaries

  • The package never touches the live audio stream. It works on finished turns, so it cannot stall the call.
  • All state lives in the profile file. The engine and tools are stateless and can run in any number of workers on one host.
  • The JSON Schema is the contract. Agents written in other languages can read and write the file directly if they follow the write protocol.

Dataflow SEQUENCE · TRANSFORMATIONS

A call has three phases. At call start the agent loads what is already known. On every user turn the audio and transcript become features, then inferences, then guidance for the next turn. At call end the session is rolled up into the person's baseline and long-term trends.

Dashed arrows are return values. Feature extraction runs before the file lock is taken, so the lock is held only for the read, reasoning and write.

High-level design HLD

Requirements

Functional

  • Record what was said and how: pitch, loudness, pauses, pace, voice quality, fluency, vocabulary.
  • Estimate emotion, communication skills, speaking style and accent.
  • Raise non-diagnostic speech indicators, only with opt-in consent.
  • Keep a personal baseline and per-session trends.
  • Let many agents read, write and leave evidence-backed observations.
  • Turn findings into concrete guidance a voice agent can apply.

Non-functional

  • Per-turn analysis well under the time an LLM takes to reply (measured: 187 ms median).
  • No lost updates with concurrent writers; no half-written files after a crash.
  • Every inference explainable: cues, confidence and method stored with it.
  • Privacy by default: consent gates, retention, transcript opt-out, erasure.
  • Light dependencies (numpy; jsonschema optional) and a language-neutral file format.

Deployment options

BUILT

Embedded library

The voice worker imports paralingo and calls the engine directly. Profiles live on the worker host's local disk. Simplest option, and correct for one host with any number of worker processes.

BUILT

MCP sidecar

The same files, exposed to LLM agents and tools over MCP stdio. Use --no-pipeline-tools to give agents read and observe access only.

NEXT STEP

Profile service

For several hosts: put the engine behind an HTTP service and swap the file store for a database row per speaker (for example Postgres JSONB with SELECT … FOR UPDATE). The schema and the tool API stay the same. Not built yet.

Cross-cutting concerns

Concurrency

  • One file per speaker, so writers only contend when they work on the same person.
  • An exclusive lock file serialises writers; a lock older than 30 s is treated as stale and broken.
  • revision plus expected_revision catches edits made from a stale read.
  • Tested with 4 concurrent agents and 20 writes: no lost updates.

Privacy and safety

  • voice_analysis off: analysis is refused. health_indicators is opt-in; turning it off deletes existing indicators.
  • store_transcripts off: only derived numbers are kept.
  • retention_days purges old sessions and observations on every write; delete() erases a speaker.
  • Indicators carry confounders and a disclaimer, and need 3 of the last 5 sessions to become persistent.

Performance (measured on this machine)

  • Acoustic analysis of a 4.6 s turn: 98 ms. Text analysis: 0.3 ms.
  • analyze_utterance end to end, profile with 60 utterances: 187 ms median, 253 ms p95.
  • end_session: 87 ms. File growth: about 4.5 KB per stored utterance.
  • Run analysis in parallel with the LLM call; guidance then applies from the next turn and adds no reply latency.

Failure handling

  • Tool calls return {"ok": false, "error": …} instead of raising, so a failed analysis never breaks the conversation.
  • If the edit body raises, nothing is written.
  • Lock timeout (10 s) returns LockTimeout; the pipeline should skip that turn's analysis and carry on.
  • Writes that fail schema validation are rejected before touching the file.
Storage constraint. Lock files are reliable on a local filesystem on one host. They are not reliable on synced folders (OneDrive, Dropbox) or on many network filesystems. This project folder is inside OneDrive, which is fine for development, but in production keep the profiles directory on local disk, or move to the profile service option above. Full-file rewrites also make write cost grow with file size; compaction keeps utterance detail for the last 20 sessions only.

Write protocol: store.edit()

  1. Create <file>.lock with an exclusive create. If it exists, retry every 10 ms; break it if older than 30 s; give up after 10 s with LockTimeout.
  2. Read the profile, or build a new one when create_if_missing is set.
  3. If expected_revision was passed and differs, raise ConcurrencyConflict.
  4. Hand the document to the caller to change. If the caller raises, release the lock and write nothing.
  5. Increase revision, set updated_at, append an audit entry (keep the last 500).
  6. Apply retention: drop expired sessions and observations, strip utterances from closed sessions beyond the last 20, blank transcripts if storage is off.
  7. Round-trip through JSON to normalise numpy values, then validate against the schema.
  8. Write to a temp file in the same folder, flush, fsync, then os.replace over the real file (retry up to 20 times on Windows sharing errors).
  9. Delete the lock file.

IntonationF0 in semitones re. median; spread p5–p95; slope over the last 0.5 s of voicingrising > +3 st/s · falling < −3 st/s

Jitter, shimmerEach period is the shift (0.8–1.2 T) that best aligns one cycle's waveform with the next, as in Praat's cross-correlation method; cycles that correlate below 0.5 are skipped; mean absolute difference over meanperiod factor 1.3 · amplitude factor 1.6 · cycle correlation ≥ 0.5
